# Pipeline Maintenance & Manual Operations Guide

While the **Off The Pace** pipeline leverages automated compilation, testing, and continuous integration, certain physical parameters, telemetry overrides, and structural documentation layers require human-in-the-loop manual synchronization.

This guide documents the **four manual domains** that must be maintained to ensure the physical baselines and statistical ratings remain mathematically accurate and sync-drift free.

---

## 1. Reference Data Overrides (Manual Seeds)

The transform pipeline relies on static CSV seeds inside `/transform/seeds/` to govern calculations where telemetry data is sparse or sensor anomalies exist.

```
                  Developer Edits Seeds (CSV) 
                              │
                              ▼
                     Run 'dbt seed' 
                              │
                              ▼
         Intermediate SQL Joins (int_event_corrections, stg_laps)
```

### 1.1. Incident & Anomaly Overrides (`seeds/raw_dim_events.csv`)
*   **What it does:** Documents race-level incidents that telemetry cannot dynamically classify (e.g. specific steward decisions, red flag scopes, and local yellow sector flags).
*   **Schema Structure:**
    ```csv
    race_id,event_type,lap_start,lap_end,description,weight_override
    2023_15,safety_car,20,23,Sargent crash in Sector 3,0.3
    2023_15,restart,24,24,Race resumption,0.7
    ```
*   **Maintenance Protocol:** When ingesting a **new racing season**, you must manually research and log the lap-boundary windows for Safety Cars, Virtual Safety Cars, and Red Flags into this CSV sheet. The downstream view `int_event_corrections` consumes this data to apply outlier weights:
    *   `0.3` for full Safety Cars.
    *   `0.5` for VSCs.
    *   `0.7` for restarts/pit laps.

### 1.2. Tyre Compound Allocations (`seeds/tyre_allocations.csv`)
*   **What it does:** Maps C1–C5 compound specifications (Pirelli’s hardness ratings) to the standard Soft/Medium/Hard designations per season per circuit.
*   **Maintenance Protocol:** Prior to running `dbt seed` for a new season, check Pirelli’s compounds allocation sheets for each track and log them here. Staging joins this seed downstream to normalize tyre compound variables.

## 2. Coefficient Fitting & Promotion Loop

Tyre wear gradients, cliff thresholds ($\tau$), and circuit fuel weight penalties ($w$) are slow-changing physical coefficients. Rather than estimating these on every run (which would introduce circular leakage in the DAG), they are fit offline and loaded as reference tables.

```
  Run Fitter (coefficients-fit) ──► Review Pending (seeds/_pending/) ──► Promote (coefficients-promote)
```

### 2.1. Re-Fitting Step-by-Step
When a new season is completed, or if a significant volume of new telemetry data is ingested:
1.  **Execute Fitter:**
    ```bash
    make coefficients-fit
    ```
    This launches the local Python Kaplan-Meier survival analysis task, generating updated wear parameters and depositing them in:
    *   `transform/seeds/_pending/compound_cliff_params.csv`
    *   `transform/seeds/_pending/circuit_reference.csv`

2.  **Manual Parameter Audit:**
    You must physically inspect the pending files to confirm mathematical soundness:
    *   **Tyre Cliffs ($\tau$):** Confirm that the estimated cliff onset laps (`compound_cliff_onset_laps`) are physically plausible (e.g., Soft compounds should sit between $12$ and $22$ laps; Hard compounds between $25$ and $45$ laps).
    *   **Weight Penalty factors ($w$):** Check that the fitted circuit penalty factors are stable (Monaco should sit near $0.025\text{ s/kg}$; Monza near $0.018\text{ s/kg}$).

3.  **Promote & Backup:**
    ```bash
    make coefficients-promote
    ```
    This script performs an atomic promotion:
    *   Backup existing seeds to `/transform/seeds/_archive/`.
    *   Overwrites `/transform/seeds/` with the pending parameters.

4.  **Rebuild schemas:**
    ```bash
    make dbt-dev-full
    ```

## 3. Reference Doc Compilation & CI Drift Checks

Custom documentation generators convert compiled dbt models (`manifest.json`), JSON schemas, CLI
variables, and macro descriptions into Markdown under **`docs/reference/`**. (These pages carry an
`_AUTOGENERATED` banner + raw `# H1`; they predate the Mintlify move and do **not** yet have Mintlify
frontmatter or `docs.json` nav entries — adapting them is open Phase 1 work, see PROJECT_PLAN.)

```
 dbt compile ──► scripts/build_reference.py ──► docs/reference/ ──► docs-ci.yml drift check (git diff)
```

### 3.1. Compilation Commands
Whenever you edit models, variables, descriptions, or macros inside the `/transform` folder, recompile
and re-run the document generators:

```bash
# Compile latest manifest
cd transform && ../.venv/bin/dbt compile --profiles-dir profiles

# Run all reference doc generators from project root
python scripts/build_reference.py
```

This runs:
*   `gen_dbt_reference.py` $\rightarrow$ `docs/reference/models/`
*   `gen_macro_reference.py` $\rightarrow$ `docs/reference/macros/`
*   `gen_schema_reference.py` $\rightarrow$ `docs/reference/schemas/`
*   `gen_cli_reference.py` $\rightarrow$ `docs/reference/cli/`
*   `gen_ml_reference.py` $\rightarrow$ `docs/reference/ml/`

### 3.2. GitHub Actions CI Drift Gate
If you change `/transform` but forget to regenerate and commit the reference Markdown, **`docs-ci.yml`
fails**. The gate re-runs the generators and diffs the output:

```bash
python scripts/build_reference.py
git diff --exit-code docs/reference/
```

To resolve a blocked merge due to doc drift:
1.  Navigate to your local repository.
2.  Run `make dbt-dev` and `python scripts/build_reference.py`.
3.  Commit and push the newly generated reference Markdown files.

## 4. Mintlify Navigation & Page Promotion

Navigation lives in **`docs/docs.json`** under `navigation.tabs[].groups[].pages` — the Docusaurus
`sidebars.ts` / `docusaurus.config.ts` are gone. New pages are **not** auto-discovered; register them
by hand.

### 4.1. Promoting a new page
1.  **Write the page** as `.mdx` under `docs/` (e.g. `docs/decomposition/new-page.mdx`) with Mintlify
    frontmatter — `title`, optional `sidebarTitle`, `description`.
2.  **Register it in `docs.json`** — add its path (no extension, relative to `docs/`) to the right
    group's `pages` array:
    ```json
    {
      "group": "The Decomposition",
      "pages": [
        "decomposition/seven-term-identity",
        "decomposition/new-page"
      ]
    }
    ```
3.  **A new top-level section** → add a `group` (or a new `tab`), not just a `pages` entry.

> The ~59 auto-generated `reference/**` pages are **not** registered here yet. Wiring them in — after
> they gain Mintlify frontmatter — is the open Phase 1 task tracked in PROJECT_PLAN.

## 6. Adding a New Season

Onboarding a new season is a single command followed by a user-gated publish. **No ML retrain required** — the headline tyre-degradation curve is a deterministic isotonic fit that re-runs automatically.

### 6.1. One command

```bash
make add-season SEASON=2025
```

This chains seven steps automatically:

| Step | What happens |
|---|---|
| 1. Ingest races | `ingest.py --season 2025 --session both` pulls lap/telemetry bronze |
| 2. Ingest standings + pits | `jolpica_client.py` pulls results + pit-stop data |
| 3. Verify bronze | `verify_bronze.py` checks counts, nulls, schema |
| 4. Re-fit isotonic curves | `fit_degradation_isotonic.py` re-fits per `circuit × era × compound` — **no ONNX retrain** |
| 5. Full dbt build | car-FE refit + all 55+ models rebuilt against new bronze |
| 6. dbt tests | All schema + singular tests must be green before proceeding |
| 7. Export + smoke test | `export_app_data.py` writes parquet + manifest; `smoke_test_season.py` asserts the season is wired |

**Stops before publish** — the new season is live locally. Inspect it with `make app-dev-local`.

### 6.2. Manual seed updates (run before step 5)

Before `dbt-dev-full`, update these seeds for the new season (see §1–2 above):

- `seeds/raw_dim_events.csv` — Safety Car, VSC, red flag lap windows
- `seeds/tyre_allocations.csv` — C1–C5 → Soft/Medium/Hard mapping per circuit

### 6.3. Era boundary (2022 only)

The current era split (`pre2022` / `post2022`) is controlled by a single knob:

- **dbt var:** `vars.era_boundary: 2022` in `transform/dbt_project.yml`
- **Fit script:** `ERA_BOUNDARY = 2022` in `transform/tasks/coefficients/fit_degradation_isotonic.py` (+ `--era-boundary` CLI arg)
- **Manifest:** exported as `stats.era_boundary` — the app reads this to set era from a loaded stint

A third regulation era (e.g. 2026 ground-effect revision) requires new era-label strings in
`int_driver_circuit_era_affinity.sql` and a new `era_boundary` value. Flag in `_roadmap/ISSUES.md`.

### 6.4. Publish (user-gated)

After local review:

```bash
make app-publish   # sync app/public/data/ → GCS CDN
```

Do **not** publish without explicit approval. The publish step is intentionally excluded from `add-season`.

### 5.2. Sync protocol

**When to sync:** a phase completes; a locked decision reverses; architecture/stack/layout changes;
scope locks or unlocks; an issue opens or resolves.

**How to sync:**
1. **In-repo plans are primary** for trajectory decisions — update the relevant plan first.
2. **Memory is secondary** — after updating a plan, summarise the change into a memory file (+ the
   `MEMORY.md` index line) so future sessions get context without re-reading every plan. Note:
   `_roadmap/` is gitignored, so decisions that must survive across machines live in memory.
3. **Cross-reference liberally** — plans link to each other and to `ISSUES.md`; memory files link back.
