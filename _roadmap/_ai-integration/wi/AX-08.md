## Decided

- Order inside `make app-data`: (1) `export_app_data.py` writes tables, `assistant_entities`, `qv_*` and `catalogue.json`; (2) `node app/scripts/build-cards.mjs` reads `app/public/data` and writes card files, `assistant/index.json`; (3) `export_app_data.py --finalize` computes the content hash over everything and writes the manifest.
- Manifest gains an `assistant` block (design 2.7): `{card_schema, catalogue_version, registry, label_version, model_version, cards:[{season, path, rows, sha256}], classes_live, classes_held}`. `model_version` is `null` until the ML cards exist (HD8).
- The Worker's tool definitions, system prompt and `CATALOGUE_VERSION` are generated from `catalogue.json`, so the Worker and the app cannot disagree (design P7, watch AXW4; the 409 on mismatch is AX-12).

## Findings that change the method

1. **The version hash would not notice a changed card.** `_content_hash` hashes only parquet file names and sizes (lines 211-218). A card whose value changes but whose file keeps the same size leaves `manifest.version` unchanged, so the acceptance "changing one card changes `manifest.version`" fails as designed. Fix minimally: `version = sha256(existing hash input + canonical JSON of the assistant block)`; the block carries each card file's sha256 of bytes. Tables keep their existing weakness (name plus size); say so in the run note and leave it alone.
2. **`--check` compares manifests with `version` and `generatedAt` removed** (`_strip`, lines 701-707) and it needs the warehouse (`run_export` exits when `DB_PATH` is missing, line 590). It cannot detect a stale card file. Add to `--check` (and to `--finalize --check`): re-hash every file named in `assistant.cards` and the catalogue, compare with the manifest, fail on any mismatch. A drift of cards from upstream data is caught by a new Make target (below) that rebuilds the cards into a temp folder and compares the hashes.
3. **`--finalize` must not need the warehouse.** It runs after build-cards from files only.
4. **The CDN sync will not carry the new folder.** `scripts/publish_cdn.sh` loops over `dimensions facts intermediates marts` (line 90) and sets cache-control on the same four (lines 112-115). Files under `app/public/data/assistant/` (cards, `qv_*`, `catalogue.json`, `assistant_entities` if placed there) would never be uploaded. Add `assistant` to both lists. Changing the script is code; actually publishing needs the owner's yes (rule 7).
5. **Writing parquet from Node is unproven.** build-cards writes canonical JSON (sorted by `id`) into a staging folder; `--finalize` converts it to ZSTD parquet in Python with a fixed `ORDER BY id`, enforces the 5 MB gate (`MAX_FILE_BYTES`) and computes the sha256. Two runs on unchanged input must give identical bytes (test it; DuckDB parquet writes are not guaranteed byte-stable across versions, so record the duckdb version in the run note).
6. `app/scripts/build-cards.mjs` is the AX-04 name; the design's `.ts` name does not run (see AX-04).

## Method

1. `export_app_data.py`: add `--finalize` (no warehouse; reads `app/public/data/assistant/`; writes card parquet partitions `assistant/cards/{season}.parquet` and `_global.parquet`, validates against the AX-01 schema column list, builds `assistant` block, rewrites `_manifest.json` with the new version) and the `--check` additions of finding 2.
2. `app/src/data/manifest.ts`: add `assistant?: AssistantBlock` to `DataManifest`; no behaviour change for existing code.
3. `Makefile`: `app-data` runs the three stages in order; add `app-cards-check` (rebuild cards to a temp dir, compare sha256 with the manifest). Do not change what `app-publish` uploads except through step 4.
4. `scripts/publish_cdn.sh`: include `assistant` in the sync and cache-control lists.
5. `worker/scripts/gen-tools.mjs` reads `app/public/data/assistant/catalogue.json` and the card registry's kind list and writes `worker/src/generated/tools.ts` exporting `SYSTEM_PROMPT`, `TOOLS`, `CATALOGUE_VERSION` (header: generated, do not edit). Content comes from two templates: `app/src/assistant/prompt/system.md`, whose content AX-21 writes (AX-10 has no step for it), and `tools.template.json` (the 7 tool schemas; AX-21 adds the `bundle` argument to `get_fact_cards`, filled from `playbook.json`). This item ships minimal valid templates so the generator is testable. The generator substitutes the view-name and card-kind enums and the one-line catalogue section, and fails if tool schemas exceed 1,400 tokens or the catalogue section 600 (design 2.6 slots). `worker/src/config.ts` then re-exports from the generated file. Commit-time check (moved from AX-12): regenerating gives no diff. The export stage lands as its own finalize module, with a one-line hook in `export_app_data.py`.
6. If HD10 is yes: add ADR-011 after ADR-010 in `architecture-decisions.mdx`, in the same `<Accordion>` format, and a short block recording AD1-AD5 (question, resolution, date) taken verbatim from the old log's decisions; do not paraphrase the rulings.

## Acceptance

- Changing one card value (same file size) changes `manifest.version`, and `--check` fails until `--finalize` is re-run (two tests).
- Re-running the pipeline on unchanged input reproduces every `assistant.cards[].sha256` and `catalogue_version`.
- `worker/src/generated/tools.ts` carries the same `catalogue_version` as the manifest (a test reads both).
- `publish_cdn.sh --dry-run` lists `assistant/` in its sync.
- Each card partition is under 5 MB.

## Tests to add

Python: hash-sensitivity, `--check` failure on a tampered card file, deterministic parquet, 5 MB gate. Node: `gen-tools` output carries the version, token bounds, stale generated file detected (`worker` vitest). Existing worker tests (16) still pass.

## Definition of done

Pipeline runs end to end on a scratch export; the tests above and `cd worker && npm test` pass; `make app-data-check` logic passes on the scratch copy; `--dry-run` publish output pasted into the run note. No CDN upload, no change under `app/public/data/` except a requested `make app-data`. Do not commit.
