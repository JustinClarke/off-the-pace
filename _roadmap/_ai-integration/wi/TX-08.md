## Method

1. **Range tests.** Replace each vacuous test with a check that can fail on today's data if it breaks: `not_null` plus a floor tied to a rule (for example `n_clean_laps >= 1`, or the TX-01 trust floor once it lands), Do not add a second CI-bracket or coverage test: TX-01's and TX-02's tests are those; mutate them in step 4. Do not write a hand-listed coverage exception list.
2. **Residual bound.** Set it by a rule written in the header before looking at the max, for example the original 15 s blow-up bound, or k × a robust spread of the residual. Fix lines 2 and 6. If the rule fails on real laps, report the laps; do not raise the bound to clear them.
3. **CI branches.** For each of the five, state why the CI value exists. Keep it only if the fixture cannot meet the full threshold, and write that reason in the file.
4. **Vacuity audit (TR-019), at least for every test guarding the three AI marts and `fct_lap_residuals`.** For each test, on the scratch copy only: `CREATE OR REPLACE TABLE` a corrupted copy of the model it reads (break exactly the property it claims to guard), run that one test with `dbt test -s <test>`, confirm it fails, then restore by rebuilding the model. Record test, mutation, result in a table in the output. A test that still passes is vacuous: fix it.
5. **Real-data check (AI-13).** Choose and record why:
   - (a) a job on a self-hosted runner, read-only on a reviewed build;
   - (b) thresholds written to hold at fixture scale;
   - (c) a local `make` gate the owner runs before every export.

   Draft the workflow or Makefile change. Do not enable `PIPELINE_ENABLED` or add secrets.

**Scratch build (never `data/dev.duckdb` or `data/ci.duckdb`):**

**Threads and oracle (the same in every TX doc):** every dbt run uses 1 thread (`threads: 1` plus `settings: {threads: 1}`). Never edit those baseline files (TX-07's `dim_events` key removal is the one exception); the owner re-takes them once, after TX-01..07 land. Copy from `<your scratchpad>/base/dev.duckdb` when the shared base build exists (one full build of the current tree at 1 thread); otherwise from `data/dev.duckdb` (copy only), which predates the v16 seal, so the unchanged rebuild before the snapshot matters.
