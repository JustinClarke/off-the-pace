# TX-14 - three models change output between identical builds

**Group:** 1 transform · **Depends on:** TX-08 · **Model/cost:** opus-5, 1d · **Blocker:** none.

**Sources:** `_evidence/TX-08-2026-11-08/PROVENANCE.txt` (finding F2, before.json, mutate.py), `transform/scripts/snapshot_model_hashes.py`, the three model SQL files named in the log.

## Problem
At 1 thread, with no source change, `fct_driver_isolation_stint` flips between two hashes (e369af61, cecbc185), and `int_pit_strategy_cost_curve` and `int_sector_residual_decomposed` also differ between rebuilds. Row counts are equal. A byte-hash baseline cannot certify anything while this is true: the oracle can go red with nothing changed.

## Method
1. On YOUR OWN scratch copy named dev.duckdb (profiles dir, threads 1 and settings threads 1, --target-path in your folder; never open data/dev.duckdb or data/ci.duckdb), rebuild each model 5 times and hash. Find which rows/columns differ between runs (row-level diff on a stable key).
2. Identify the cause per model: unordered aggregation (first/any_value, array_agg without ORDER BY, LIMIT without ORDER BY), ties in ROW_NUMBER/RANK, float summation order, or a volatile column the snapshot script does not exclude.
3. Fix with a deterministic ORDER BY / tie-break in the model, or add the volatile column to the snapshot script's exclusion list if it is genuinely not data. Do NOT change values: show the old and new hash sets and that every value is within the set of previous outputs.

## Acceptance
Five consecutive rebuilds of each of the three models give one hash each; all other model hashes are unchanged versus your before-snapshot. Owner decision: if a fix changes a value a published page shows, stop and report it. Never edit the committed baselines.
